# Dependency / Supply-Chain Security Model

**Status:** Implemented and verified (Phase A3). Supersedes the Phase 4A version of this
document, which described a future *plan* (`pnpm`, `pip-tools`/`uv`, `cargo audit` in CI,
SBOM generation) rather than what was actually built. None of that plan was carried out;
what follows is the dependency-management model that actually exists in this checkpoint,
independently re-verified during Phase A3 rather than assumed from that earlier plan.

**Related:** `docs/architecture/18-packaging-release-architecture.md`,
`.github/workflows/ci.yml` (Phase A2), `requirements.txt`, `requirements.lock.txt`,
`frontend/package-lock.json`, `keystore-core/Cargo.lock`, `sidecar-core/Cargo.lock`,
`src-tauri/Cargo.lock`.

## How are Python dependencies controlled?

Two files, two different jobs:

- **`requirements.txt`** — the authoritative *contract*: minimum-version (`>=`) floors,
  organized into commented sections (Sidecar API, Desktop GUI, CLI/reporting, Testing).
  Floors are intentional project policy (not an oversight) — see that file's own header.
  Installing from this file lets floors "float forward" to newer compatible releases.
- **`requirements.lock.txt`** — an additive, *exact-pin* snapshot of every distribution
  (direct **and** transitive) that a clean `pip install -r requirements.txt` actually
  resolved to in a verified-good environment, captured with `pip freeze --local`. This is
  what CI installs from, for byte-for-byte reproducible runs. It is regenerated by
  re-running the install + freeze whenever `requirements.txt` changes, or when drift is
  suspected — see the file's own header for the exact two commands and the Phase A3
  regeneration note for a real example of why an incomplete freeze is worse than no freeze
  (a previous snapshot silently omitted three transitive packages, which let them float
  unpinned on every install — fixed in Phase A3, see requirements.lock.txt's header).

No `pyproject.toml`, Poetry, or `uv` — deliberately. This project has no build/packaging
step that consumes a `pyproject.toml` (packaging goes through PyInstaller directly against
`app/`, see `packaging/`), so adopting one of those tools would add a second source of
truth for the same information without solving a problem the two-file scheme above doesn't
already solve. Revisit only if a real need appears (e.g. publishing `app/` as an installable
package).

**Supported Python version:** 3.12 (`.python-version`, matches `.github/workflows/ci.yml`'s
`setup-python` step and the version every verification in this checkpoint's history was run
against — see `docs/architecture/PHASE4B_ARCHITECTURAL_FINDINGS.md`).

## How are Node dependencies controlled?

**`frontend/package.json`** (direct dependencies + devDependencies, npm scripts) and
**`frontend/package-lock.json`** (npm's own resolved-graph lockfile, `lockfileVersion: 3`).
`package-lock.json` is authoritative for exact resolved versions; `npm ci` (used by CI and
recommended for contributors) installs *only* from the lockfile and fails outright if it's
missing or out of sync with `package.json` — verified in Phase A3 (`npm ci` from a clean
`node_modules` state succeeds; `npm test`, `npm run typecheck`, `npm run build` all still
pass unchanged: 1006 tests, clean typecheck, 189-module build).

**Supported Node version:** documented as of Phase A3 via `frontend/.nvmrc` (`22`) and
`frontend/package.json`'s new `engines.node` field (`>=20 <23`) — neither existed before;
both were previously undocumented even though CI (`actions/setup-node`) already pinned
Node 22. This is documentation only, not a version change: nothing about the supported
range changed, it just wasn't written down anywhere a contributor would find it.

## How are Rust dependencies controlled?

Three independent crates (no Cargo workspace — `src-tauri` depends on `keystore-core` and
`sidecar-core` via path dependencies, but each has its own `Cargo.toml`/`Cargo.lock`), each
with its **own committed `Cargo.lock`**. This is correct for all three, not just
`src-tauri`: `Cargo.lock` should be committed for *any* crate built and tested as a
top-level target with `cargo test`/`cargo build` (the Rust-project convention that only
crates meant to be consumed as libraries by others, i.e. published to crates.io, should
omit it) — `keystore-core` and `sidecar-core` are both tested standalone in CI, not just
pulled in as path dependencies, so committing their locks is deliberate, not an oversight.

Re-verified in Phase A3 with `cargo check --locked` (fails loudly if `Cargo.lock` is stale
relative to `Cargo.toml`): `keystore-core` and `sidecar-core` both pass, confirming both
locks are current. `src-tauri`'s lock could not be verified the same way in this sandbox —
see "What is intentionally not covered" below; `.github/workflows/ci.yml`'s `rust` job
verifies it on every push with a current toolchain instead.

## Which files are authoritative?

| Ecosystem | Authoritative for *what to install* | Authoritative for *exact reproducible versions* |
|---|---|---|
| Python | `requirements.txt` | `requirements.lock.txt` |
| Node | `frontend/package.json` | `frontend/package-lock.json` |
| Rust | `{keystore-core,sidecar-core,src-tauri}/Cargo.toml` | the matching `Cargo.lock` |

## How does CI install dependencies?

`.github/workflows/ci.yml` (Phase A2, unchanged in structure by A3):

- Python job: `pip install -r requirements.lock.txt` (exact pins, not the floors).
- Frontend job: `npm ci` (lockfile-only, fails on drift).
- Rust job: `cargo test`/`cargo check` against each crate's committed `Cargo.lock`
  (Cargo uses the lock automatically; no extra flag needed for that job's normal invocation).

## How should contributors update dependencies?

See "Dependency update policy" below.

## What is intentionally NOT covered

- **No automated vulnerability scanning in CI** (no `pip-audit`/`cargo-audit`/`npm audit`
  step). A3 ran these manually once as a baseline (see the Phase A3 report's Security
  Findings) rather than wiring them into CI — turning that into an enforced, always-green
  CI gate is a deliberate future-phase decision (it needs a policy for what severity fails
  the build and how false positives/unfixable transitive findings are handled), not
  something to bolt on silently here.
- **No SBOM generation.** Real value at release/distribution time, not before — unchanged
  from the original Phase 4A assessment, just no longer described as imminent.
- **No Rust toolchain-version pin (`rust-toolchain.toml`).** `keystore-core`/`sidecar-core`
  declare `rust-version = "1.75"` (a floor, in-manifest) and CI's `rust` job intentionally
  tracks whatever `dtolnay/rust-toolchain@stable` currently resolves to for `src-tauri`
  (which needs a newer toolchain than 1.75 provides — see that job's own comments in
  `ci.yml`). Pinning an exact toolchain version is a reasonable future hardening step, not
  done here to avoid the workflow silently going stale against a fixed old Rust release.
- **`src-tauri`'s `Cargo.lock` currency is CI-verified, not sandbox-verified.** This
  sandbox's apt-provided Rust (1.75.0) cannot resolve `src-tauri`'s dependency graph at all
  (`edition2024` requirement — see `.github/workflows/ci.yml`'s `rust` job comments), so
  `cargo check --locked` could not be run against it here. `.github/workflows/ci.yml`
  already runs plain `cargo check`/`cargo test` for it on every push with a current
  toolchain, which would fail the same way a stale lock would (a resolve mismatch), so the
  gap is in *this document's* local verification, not in the project's actual safety net.

## Dependency update policy

1. Change the floor/version in the authoritative manifest (`requirements.txt`,
   `frontend/package.json`, or the relevant crate's `Cargo.toml`) — never hand-edit a
   lockfile.
2. Regenerate the matching lockfile using the ecosystem's own tool:
   `pip install -r requirements.txt && pip freeze > requirements.lock.txt` (Python,
   see that file's own header for the exact commands), `npm install` (Node — updates
   `package-lock.json` in place), `cargo update -p <crate>` or `cargo build` (Rust —
   updates `Cargo.lock` in place).
3. Re-run the full local test suite for the affected ecosystem (or all three, for a
   shared/transitive dependency) before opening a PR — the same commands
   `.github/workflows/ci.yml` runs.
4. Let CI pass on the PR — it re-installs from the updated lockfile/pin file, so a
   regenerate-then-forget-to-commit mistake fails loudly instead of silently.
5. One dependency (or one clearly-related group, e.g. a security patch release across a
   package and its own sub-dependencies) per change. Do not fold an unrelated dependency
   bump into a feature/bugfix PR, and do not batch unrelated ecosystem-wide upgrades into
   one PR — each makes the other's regression, if any, harder to bisect.
6. A major-version bump (Python, Node, or Rust) gets called out explicitly in the PR
   description, even if tests pass — passing tests confirm no *observed* regression, not
   the absence of any behavior change.
