# §20 Security Hardening — CSP/Loopback Wildcard Closure (Part 2D-2)

## Selected Control

```text
Control:
IPC/CSP loopback wildcard reconciliation

Authority:
docs/security/ipc-security-model.md, "CSP / Loopback Wildcard" section;
Part 2D-1 backlog reconciliation (docs/security/PHASE4O_SECURITY_P2D1_BACKLOG_RECONCILIATION.md)

Threat:
An overly broad connect-src (any loopback port, not just the sidecar's) widens the
blast radius available to any future webview compromise (malicious/compromised JS
dependency, XSS) -- it could reach other loopback services on the same machine, not
just the intended sidecar.

Asset:
Other loopback-bound services/processes on the same machine, reachable from a
compromised webview via fetch/invoke.

Attack surface:
The Tauri webview's outbound network access as constrained by src-tauri/tauri.conf.json's
CSP connect-src directive.

Security invariant:
The webview can only ever reach the intended sidecar process, enforced at the
loopback-binding + Tauri-capability boundary rather than by the CSP string alone.

Enforcement boundary:
Sidecar process binding (app/api/entrypoint.py, always 127.0.0.1) + Tauri capability
restriction on frontend-invokable commands. The CSP wildcard itself is retained as
loopback-scoped defense-in-depth, not narrowed, per the decision below.

Required regression:
Existing capability-manifest snapshot regression (Part 2A) and export/IPC suites,
which already exercise the invariants this decision relies on. No new test is
generated by a documentation-only decision.
```

## Decision Gate Re-Audit

Independently re-verified from source, not assumed from the Part 2D-1 report:

- `src-tauri/tauri.conf.json` CSP is exactly `default-src 'self'; style-src 'self'
  'unsafe-inline'; connect-src 'self' http://127.0.0.1:*` -- unchanged, wildcard present.
- `app/api/entrypoint.py` performs a real synchronous stdout port handshake at sidecar
  startup (OS-assigned ephemeral port by default, one decimal line on stdout).
- `src-tauri/src/sidecar.rs` reads exactly one line from the child process's stdout to
  learn the bound port (`port(&self) -> Option<u16>`), confirming the Rust side consumes
  a real, runtime-known port rather than a hardcoded one.
- `frontend/src/shared/api/client.ts` resolves the sidecar origin exclusively via
  `invoke("get_sidecar_origin")` and never hardcodes or re-derives a port.

This confirms the Part 2D-1 finding: the original blocker recorded in
`ipc-security-model.md` ("no sidecar supervisor exists yet to hand a concrete port to
the CSP") is no longer true. A concrete port is available at runtime, so this item is
no longer merely a documentation placeholder for a future decision -- an explicit
decision is now due.

## Why Option (b), Not Option (a)

The doc's own pre-offered choice was:

- **(a)** narrow the CSP to the actual resolved sidecar port via Tauri's runtime CSP
  injection (`src-tauri/src/lib.rs`, compiled Rust), or
- **(b)** keep the wildcard (already loopback-scoped -- no non-local origin is ever
  reachable) and formally name loopback binding + Tauri capability restriction as the
  actual, primary enforcement boundary, with the wildcard as accepted defense-in-depth.

This sandbox has no `cargo`/`rustc` toolchain:

```
$ which cargo rustc
(not found)
```

This is unchanged from every prior part in this §20 chain (Part 2C-2 through Part
2D-1). A narrow-CSP implementation touching `src-tauri/src/lib.rs` cannot be compiled,
exercised, or regression-tested here -- landing it unverified would violate the
"never weaken a test to obtain PASS" / "must exercise real production behavior"
requirements for this chain, since there would be no way to confirm the Rust code even
builds. Option (b) is therefore selected: it requires no unverifiable Rust change, and
it matches the doc's own explicitly pre-approved fallback rather than an invented
workaround.

**This is a documentation decision, not a new production code change.** No file under
`src-tauri/src/`, `app/`, or `frontend/src/` was modified. The only production
touchpoint (`tauri.conf.json`'s CSP string) is unchanged.

## Verdict

**PASS WITH CONDITIONS**

Condition: this closure accepts a real, non-zero residual risk (a compromised
webview could reach any loopback service, not just the sidecar) because the
stronger remediation (narrow CSP, option (a)) requires a Rust toolchain this
sandbox does not have. If a Rust-capable environment becomes available, option
(a) should be implemented and adversarially verified as a strictly stronger
follow-on; this document explicitly does not claim that follow-on is unnecessary.
