# IPC Security Model

**Status:** Documentation Foundation (Phase 4A); CSP/loopback-wildcard item closed
Part 2D-2 (§20 security hardening).
**Related:** ADR-006, `docs/architecture/05-ipc-architecture.md`,
`docs/contracts/ipc-rules.md`, `docs/contracts/error-model.md`.

## CURRENT STATE

No IPC boundary exists today — see `docs/contracts/ipc-rules.md` current-state note.

## TARGET STATE (PROPOSED)

- The Python sidecar binds to `127.0.0.1` only — never `0.0.0.0`. This is called out
  explicitly as a top security risk to actively guard against (Master Plan Top-10 security
  risks, #4), not merely a default assumed to hold.
- The listening port is ephemeral, chosen at sidecar startup, and handed to the frontend only
  via a Tauri command — it is never hard-coded or predictable, reducing the value of any
  local port-scanning attempt by another process on the same machine.
- Every command payload is validated against its schema before reaching domain logic
  (`docs/contracts/command-model.md`); malformed payloads are rejected with
  `INVALID_COMMAND_PAYLOAD` (`docs/contracts/error-model.md`), never best-effort parsed.
- The `GET /events` SSE endpoint requires the same-origin/loopback constraints as commands —
  it is not a separately-secured, more permissive channel.
- No authentication token is required for loopback-only, single-user desktop use in the
  initial design — the security boundary is process/network isolation (loopback binding +
  Tauri capability restriction on the frontend's ability to reach other origins), not a
  credential. This is flagged as a decision to revisit if the architecture ever supports
  multi-user or remote access (out of current scope).

## CSP / LOOPBACK WILDCARD (CLOSED — Part 2D-2, option (b))

`src-tauri/tauri.conf.json`'s CSP is:

```
connect-src 'self' http://127.0.0.1:*
```

This permits the frontend to `fetch`/`invoke` any loopback port, not just the one the
sidecar actually uses. This was originally logged (Phase 4A foundation checkpoint) as a
**known, temporary looseness** pending Phase 2A. Phase 2A has since landed the real
sidecar supervisor and HTTP-calling frontend, so the original blocker no longer applies,
and this item is now formally closed as follows.

- **What changed since the original note:** `app/api/entrypoint.py` performs a
  synchronous stdout port handshake at sidecar startup; `src-tauri/src/sidecar.rs` reads
  that handshake and stores the bound port; `frontend/src/shared/api/client.ts` resolves
  the sidecar's origin at runtime exclusively via the `get_sidecar_origin` Tauri command
  and never hardcodes or re-derives a port itself. A concrete port value is therefore
  available at runtime, which the original note said was the precondition for reconciling
  this item.
- **Decision: option (b), not option (a).** The CSP wildcard is kept as-is
  (`http://127.0.0.1:*`) rather than narrowed to the single resolved sidecar port.
  Narrowing (option (a)) would require injecting a runtime-known port into Tauri's CSP
  construction in `src-tauri/src/lib.rs` at window-build time — a Rust-side change that
  cannot be implemented and verified end-to-end in a sandbox without a `cargo`/`rustc`
  toolchain (confirmed absent in every part of this §20 chain, including this one). Rather
  than land an unverifiable Rust change, this closure formally adopts the doc's own
  pre-offered fallback.
- **Accepted primary boundary:** the security invariant this control protects — that the
  webview cannot reach an arbitrary process on the machine, only the intended sidecar — is
  enforced by loopback binding (the sidecar only ever binds `127.0.0.1`, never `0.0.0.0`,
  per TARGET STATE above) combined with the Tauri capability restriction on what the
  frontend is permitted to invoke. Both of those are the actual enforcement boundary; the
  CSP wildcard's remaining role is loopback-scoped defense-in-depth on top of them, not the
  primary control. It does **not** permit reaching any non-loopback origin — that
  restriction was never the gap.
- **Residual risk, accepted:** if the webview were ever compromised (e.g. a
  malicious/compromised JS dependency, or an XSS vector), it could reach any loopback
  service on the machine via `fetch`, not only the intended sidecar port. This is a real
  but narrow widening of blast radius versus a port-scoped CSP, and is accepted rather than
  eliminated because eliminating it requires the unverifiable Rust change described above.
  No live exploitation path (no XSS/JS-injection vector) exists in this codebase today.
- **Regression guard:** no new test is generated by this documentation decision. The
  invariants it relies on — loopback-only binding and capability-restricted frontend
  access — remain covered by the existing capability-manifest snapshot regression (Part
  2A, `tests/test_architecture_capability_snapshot.py`) and the export/IPC suites. If a
  Rust toolchain becomes available, revisit option (a) (narrow the CSP to the resolved
  port) as a strictly stronger follow-on; this closure does not preclude that.

This section exists so a future implementer does not mistake this for an unreviewed
default — the choice of (b) over (a) here was explicit and tooling-constrained, and is a
security decision to revisit if a Rust build environment becomes available.

## MIGRATION NOTES

Established in Phase 4D, hardened and security-tested in Phase 4M
(`docs/testing/testing-architecture.md`: "malformed-command payloads against the API
boundary").

## UNKNOWN / REQUIRES VERIFICATION

Whether any additional OS-level sandboxing (e.g. Windows Firewall scoping for the sidecar
process) is warranted beyond loopback binding is an open question, not resolved by this
document — tracked as a future hardening consideration rather than a current gap, since
loopback binding alone already prevents off-machine reachability.
