## 3. Lockfile / reproducibility decision

The project already committed to npm (frontend `package.json` has no `packageManager`
field pointing elsewhere, and no `yarn.lock`/`pnpm-lock.yaml` existed) and to Cargo (the only
possible Rust package manager). Both lockfiles were generated against the existing
dependency declarations with **no version changes** — `^18.x`/`^5.x` ranges in
`package.json` are untouched, per the task's explicit "do not turn this into a
dependency-upgrade project" instruction. `npm audit` reports 2 known advisories (1 moderate,
1 high) in `esbuild`/`vite`'s **development-server-only** attack surface (a malicious website
could talk to the dev server); fixing requires a breaking `vite@8` upgrade, which is out of
scope for a reproducibility-only pass and is noted here as a known, deferred item rather than
silently fixed or silently ignored.

## 4. Canonical development workflow (documented)

Frontend-only work:
```
cd frontend
npm install
npm run dev        # Vite dev server on :1420
npm run build       # tsc --noEmit && vite build → frontend/dist
npm run typecheck   # tsc --noEmit only
```

Full desktop app (from `src-tauri/`, using the corrected config):
```
cd src-tauri
cargo tauri dev      # runs `npm run dev` with cwd=../frontend, connects to :1420
cargo tauri build    # runs `npm run build` with cwd=../frontend, bundles ../frontend/dist
```

This works with the actual two-directory layout (no root `package.json` is introduced —
per the task's stated preference to keep the frontend self-contained), does not depend on
an undocumented working directory (the `cwd` is now explicit in `tauri.conf.json` itself,
not assumed from whatever directory a developer happens to run the command from), and no
new tooling was introduced.
